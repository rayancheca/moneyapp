## robinhood
SUMMARY: Robinhood monthly account statements are PDFs generated within the first ~2 weeks of the following month (quarterly instead when a month has no activity); the in-app archive is not officially capped and community reports indicate statements remain available back to account opening, but no official lookback window is published. Each statement contains an account summary with beginning and ending portfolio value plus a holdings table (symbol/description, quantity, market price, market value) and chronological account activity — good for point-in-time snapshots. Crypto is the weak spot: Robinhood Crypto is a separate legal entity (Robinhood Crypto, LLC), the official docs explicitly exclude "futures, crypto, and spending account activity" from the self-serve account activity reports, and community/vendor evidence on whether crypto positions appear on the monthly brokerage statement PDF conflicts across years — treat crypto-on-statement as unreliable. The self-serve account activity report (Account → Reports and statements → Account activity reports) produces a CSV over any user-chosen start/end date range for brokerage and retirement accounts, generated in ~2-24 hours and delivered as an in-app download (notification, not an emailed link), with columns Activity Date, Process Date, Settle Date, Instrument, Description, Trans Code, Quantity, Price, Amount — covering equity trades, options, dividends, interest, fees, and transfers but NOT crypto. For crypto, the free structured options are the annual tax-season exports: a Consolidated 1099 PDF (which for tax year 2025 combines Securities, Crypto/1099-DA, Derivatives, and Money into one PDF, available by Feb 17, 2026) plus per-entity CSV transaction files released after the 1099s. Statement PDFs are considered among the more consistently formatted brokerage statements by parsing vendors, but for transactions the CSV is the far safer machine-readable source.

SUMMARY: For ~50 US tickers with on-demand quotes a few times daily plus rare 2-year EOD backfills, the yahoo-finance2 npm package is the strongest primary source in mid-2026: it is very actively maintained (v3.15.4 published 2026-07-01, repo pushed 2026-07-07), its crumb/cookie auth still works, batch quote() covers all 50 tickers in one request, and chart() returns 2y+ of adjusted daily history with no API key. Stooq remains the best key-free fallback for daily EOD history (lowercase symbol + ".us" suffix via q/d/l/ CSV, adjusted closes, 30+ years depth), but it now serves a JavaScript SHA-256 proof-of-work anti-bot challenge and returned "Access denied" from a datacenter IP in my live test — it should work from the user's residential Mac but has an undocumented low daily hit cap ("Exceeded the daily hits limit"). Alpha Vantage free is confirmed at 25 requests/day, which cannot even cover one 50-ticker quote pass and whose free daily endpoint is unadjusted, so it is only viable as a last-resort slow backfill. Finnhub free (60 calls/min) is a good quote fallback but excludes historical candles entirely; Twelve Data free (800 credits/day) does include daily EOD history but its 8 credits/minute throttle makes a 50-ticker pass take ~7 minutes. Recommended pairing: yahoo-finance2 primary for quotes and history; Stooq q/d/l/ CSV as history fallback plus Finnhub /quote as quote fallback behind a common provider interface.

- [verified] Stooq daily-history CSV endpoint format is https://stooq.com/q/d/l/?s=aapl.us&i=d (optional &d1=YYYYMMDD&d2=YYYYMMDD), symbols are lowercase ticker + ".us" suffix for US equities/ETFs, no API key
    Endpoint exists and responds HTTP 200 (confirmed by my live curl test 2026-07-08). Symbol convention AAPL.US / MSFT.US / TSLA.US confirmed by QuantStart's Stooq article and pandas-datareader's Stooq reader docs. i=d selects daily interval; weekly/monthly use i=w / i=m.
- [verified] As of July 2026 Stooq fronts q/d/l/ with a JavaScript SHA-256 proof-of-work anti-bot challenge, and even after solving it my requests from this (datacenter) IP got "Access denied"
    First-hand test 2026-07-08: plain curl to stooq.com/q/d/l/ returned an HTML page requiring the client to brute-force a SHA-256 nonce with a 4-hex-zero prefix and POST it to /__verify. I solved the PoW programmatically (nonce 46789, verify returned 200), but the subsequent CSV request returned the literal body "Access denied". This means naive fetch() from a server/CI IP will NOT work; behavior from a residential Mac IP is expected to be better (Portfolio Performance forum users still recommended Stooq CSV downloads in October 2025) but I could not verify it from this environment.
- [likely] Stooq has an undocumented, low daily request cap; exceeding it returns "Exceeded the daily hits limit" instead of data. No verified number exists
    Reported consistently by Fund Manager forum (2022-2023), AmiBroker forum, and Wealth-Lab wiki. Community estimates vary (tens to low hundreds of hits/day per IP); no official documentation. For this app's usage (a few quote refreshes + rare history backfills, ~50 tickers) a one-time 50-request backfill could plausibly hit the cap in a single day — spreading the backfill over 2 days or throttling is advisable.
- [uncertain] Stooq's current-quote endpoint stooq.com/q/l/?s=aapl.us&f=sd2t2ohlcv&h&e=csv returned HTTP 404 in my July 2026 tests, even with a browser User-Agent and a PoW-verified session
    The historical quote-CSV endpoint widely documented in older tooling did not resolve for me while q/d/l/ on the same session returned 200. This could be IP-conditional (Stooq may serve 404 to blocked ranges) or the endpoint may have been removed/relocated. Treat Stooq's live-quote CSV as unreliable for automation as of mid-2026 and verify from the target machine before depending on it; the daily-history q/d/l/ endpoint is the safer Stooq surface.
- [likely] Stooq US daily data quality is good: close prices are split/dividend-adjusted, and daily history for some US stocks goes back 30+ years
    QuantStart verified adjustment behavior against Apple's Aug 2020 4-for-1 split (no artificial discontinuity). Caveat: adjustment methodology is unpublished, so cross-checking a couple of tickers against another source at ingest time is prudent.     npm registry shows a steady release cadence: 3.14.2 (May 28), 3.14.3 (May 29), 3.15.0-3.15.2 (May 30), 3.15.3 (Jun 12), 3.15.4 (Jul 1, 2026). - [likely] Finnhub free tier: 60 API calls/minute, real-time US quotes (/quote) included free, but historical candles (/stock/candle) are premium-only and return 403 on free keys
    The 60 calls/min free limit is consistently documented across Finnhub docs/pricing and third-party comparisons. So Finnhub covers need (a) — a 50-ticker quote refresh fits in one minute — but cannot cover need (b) at all. Requires a free API key. Note: I could not fetch finnhub.io/docs directly (403 to my fetcher), so per-second burst caps are unconfirmed.
- [likely] Twelve Data free (Basic) tier: 800 credits/day (resets 00:00 UTC) and 8 credits/minute; /time_series daily EOD IS included free for US equities at 1 credit per symbol, up to 5000 bars per request
    2 years of daily history (~504 bars) for one ticker costs exactly 1 credit, so a full 50-ticker backfill is 50 credits — trivially within the daily quota. The binding constraint is the 8-credits/minute throttle: any 50-ticker operation (quotes or history) takes ~7 minutes with client-side throttling. Fine for the rare history backfill; awkward for on-demand quote refreshes. Requires a free API key.
- [likely] For this exact use case, yahoo-finance2 minimizes request volume by an order of magnitude versus every keyed alternative
    One quote() call covers all 50 tickers, so 3-4 refreshes/day is 3-4 HTTP requests total (vs 150-200 calls/day on Finnhub/Twelve Data per-symbol models). History backfill is 50 chart() calls once. This request profile is far below any level that has historically triggered Yahoo rate-limiting for residential users, and it runs from the user's own Mac IP, not a datacenter.

RECOMMENDATION: PRIMARY: yahoo-finance2 (npm) for both quotes and history. It is the only free source that satisfies both needs with no API key: quote(['AAPL','VOO',...]) fetches all ~50 tickers in a single request a few times per day, and chart(symbol, { period1: 2y ago, interval: '1d' }) returns adjusted daily EOD for the rare backfill. It is demonstrably healthy in mid-2026 (v3.15.4 on 2026-07-01, commits through 2026-07-07, crumb breakages patched within days), and running from the user's residential Mac avoids the datacenter-IP blocking that plagues unofficial Yahoo access. FALLBACK: split by need — (b) history: Stooq q/d/l/ CSV (https://stooq.com/q/d/l/?s=aapl.us&i=d, lowercase + .us, adjusted closes, no key), throttled to well under ~50 requests/day and spread over 2 days for a full backfill, with graceful handling of the "Exceeded the daily hits limit" / "Access denied" text bodies and the possibility of a JS proof-of-work interstitial; (a) quotes: Finnhub free /quote (free key, 60 calls/min covers a 50-ticker pass in under a minute). Architecturally: define a PriceProvider interface (getQuotes(symbols[]), getDailyHistory(symbol, from, to)) with per-provider adapters, persist every fetched bar/quote into SQLite immediately so the app degrades to last-known prices when all providers fail, and validate provider CSV/JSON at the boundary (Stooq returns error text with HTTP 200). Skip Alpha Vantage entirely (25 req/day, unadjusted free daily data); keep Twelve Data as an optional third adapter for history only (800 credits/day is ample, but 8 credits/min makes 50-ticker quote refreshes take ~7 minutes). Caveats flagged: my Stooq tests ran from a datacenter IP, so verify q/d/l/ and especially the q/l/ quote endpoint (which 404'd for me and may be gone) from the actual Mac before finalizing the fallback wiring.

## ormChoice
SUMMARY: For a local-first, single-user Next.js App Router app with a SQLite file on disk, Drizzle ORM with better-sqlite3 is the stronger fit in mid-2026. Drizzle's better-sqlite3 driver is the only mainstream ORM path that gives truly synchronous transactions (verified in drizzle-orm source: the transaction callback returns T, not Promise<T>, and wraps better-sqlite3's native client.transaction()), which matters for correctness-critical statement-import/reconciliation batches. Prisma 7 (GA Nov 19, 2025, latest 7.8.0) is now Rust-free and ships an official @prisma/adapter-better-sqlite3 adapter, closing much of the performance gap, but its $transaction API remains async-only, its v7 migration/config overhaul (prisma.config.ts, ESM-required, migrate-dev behavior changes) is still settling, and SQLite lock handling has a history of poor error mapping. On the driver side, better-sqlite3 v12.11.1 ships prebuilt binaries for Node 20-26 and is dramatically faster than @libsql/client for local-file batch inserts (community benchmarks show 50-130x gaps on inserts in libsql issue #1850); the main friction (NODE_MODULE_VERSION mismatches, Turbopack bundling of .node files) is well-mitigated because Next.js includes better-sqlite3 in its default serverExternalPackages list and Next 16.1 fixed transitive externalization in Turbopack. The one Next-specific pattern you must apply is a globalThis-cached singleton connection to survive dev hot-reload, plus enabling WAL mode at startup. One caveat: Drizzle's stable line is 0.45.2 while v1.0 sits at rc.4 (Jun 27, 2026), so pin 0.45.x or the RC deliberately.

- [verified] Drizzle ORM's better-sqlite3 driver supports fully synchronous transactions
    In drizzle-orm/src/better-sqlite3/session.ts, BetterSQLiteSession extends SQLiteSession<'sync',...> and its transaction<T>(cb: (tx) => T): T signature is synchronous, wrapping better-sqlite3's native client.transaction(). This means an import/reconciliation batch runs atomically with no await points and no event-loop interleaving — exactly the semantics wanted for correctness-critical batch writes. Nested transactions map to SQLite savepoints; tx.rollback() throws to abort.
- [verified] Prisma transactions are async-only; no synchronous transaction API exists
    Prisma offers sequential $transaction([...]) batches and interactive $transaction(async (tx) => {...}) callbacks — both Promise-based, with a default interactive-transaction timeout (5s) and documented warnings against long-running callbacks. There is no sync path even with the better-sqlite3 adapter, because the client core is async throughout. For a single-writer SQLite file this adds interleaving risk between concurrent route handlers mid-transaction.
- [verified] Prisma 7 GA'd November 19, 2025: Rust query engine removed, driver adapters required for all databases, SQLite via @prisma/adapter-better-sqlite3
    Prisma 7.0.0 made the TypeScript-only 'Rust-free' client the default (~90% smaller bundles, claimed up to 3x faster queries — contested in some community benchmarks; Prisma published a methodology response). Breaking changes: ESM required ('type':'module'), generator renamed prisma-client with mandatory custom output path, CLI configured via prisma.config.ts, env vars no longer auto-loaded, prisma migrate dev no longer auto-generates the client or auto-seeds, client middleware and metrics removed. Latest on npm as of research date: prisma 7.8.0 (checked via npm registry).
- [likely] Prisma's Rust-free client + driver adapters for SQLite are mature/GA in 2026, but the v7 ecosystem transition is still settling
    The queryCompiler/driverAdapters path was Early Access in v6.x (Rust-free preview for PostgreSQL/SQLite announced in v6.9.0, June 2025) and became the default in v7 (Nov 2025). @prisma/adapter-better-sqlite3 is official and documented. Community reception is mixed-positive: reports of faster local performance, but GitHub issues dispute the 3x benchmark claims, and the migrate/config overhaul (prisma.config.ts, seeding changes) generated upgrade friction through early 2026.
- [verified] Drizzle ORM stable is 0.45.2; v1.0 is at release-candidate stage (1.0.0-rc.4) as of late June 2026
    Checked npm dist-tags directly: latest=0.45.2 (published 2026-03-27), rc=1.0.0-rc.4 (2026-06-27), beta=1.0.0-beta.22. GitHub releases confirm rc.1 (Apr 30, 2026) through rc.4 (Jun 27, 2026). The v1 line includes a reworked relational query builder and node:sqlite support in drizzle-kit. Practical implication: pin 0.45.x for maximum stability today, or adopt 1.0-rc knowing GA is imminent; the core SQL builder and better-sqlite3 driver APIs are stable across both.
- [verified] better-sqlite3 v12.11.1 (June 15, 2026) ships prebuilt binaries for Node 20.x through 26.x
    Checked the npm registry directly: engines field is 'node': '20.x || 22.x || 23.x || 24.x || 25.x || 26.x'. Historical NODE_MODULE_VERSION-mismatch pain (WiseLibs/better-sqlite3 issues #549, #797, #1393, #1437) occurs when a new Node major lands before prebuilds are published or when node_modules is carried across Node upgrades; fix is 'npm rebuild better-sqlite3' or reinstall. On a single dev Mac with a pinned Node LTS this is a minor, well-understood annoyance, not a blocker. No Electron in this stack, so electron-rebuild issues don't apply.
- [likely] @libsql/client is substantially slower than better-sqlite3 for local-file batch inserts
    tursodatabase/libsql issue #1850 (Nov 2024) documents libsql taking ~23,322ms to insert 10,000 records vs ~400ms for better-sqlite3 (~50-130x depending on environment); libsql-js issue #183 (Apr 2025) confirms @libsql/client routes local files through libsql-js with the same underlying cost. Later benchmarks show libsql improving (into the ~70ms range for batched inserts) but still behind better-sqlite3 (~20-23ms for 5k inserts). @libsql/client latest is 0.17.4 (June 15, 2026, checked on npm). Its main advantage — same code for local file and remote Turso — is irrelevant for a Mac-local single-user app. Note the benchmark issues are 2024/2025-era; the gap has narrowed but no source shows par
- [verified] Drizzle supports better-sqlite3, libsql, and node:sqlite as first-class SQLite drivers; better-sqlite3 is its longest-supported sync driver
    Drizzle's SQLite docs list libsql, node:sqlite, and better-sqlite3 as native drivers (plus bun:sqlite, D1, sqlite-proxy). better-sqlite3 is the canonical synchronous driver; drizzle-kit can now run migrations and Studio over node:sqlite too (added in the v1.0 beta line, npm tag 'kit/node-sqlite', Mar 2026). libsql support is equally first-class but async and geared toward Turso.
- [likely] node:sqlite (built-in DatabaseSync) reached Release Candidate in Node 25.7.0 (Feb 2026) and is stabilized in Node 26
    The --experimental-sqlite flag was dropped in v22.13.0/v23.4.0 (module usable without flag but still experimental); Node 24 LTS added timeout options for lock contention, createAggregateFunction, etc.; RC status came in v25.7.0 (Feb 24, 2026), stable in v26. It is a viable zero-native-dependency alternative to better-sqlite3 (sync API, no rebuild issues), and Drizzle/drizzle-kit already support it — but it is newer, and on Node 24 LTS (the likely runtime in mid-2026) it is not yet marked stable.
- [verified] Next.js automatically externalizes better-sqlite3 (default serverExternalPackages), and Next 16.1 fixed Turbopack transitive-dependency externalization
    better-sqlite3 is on Next.js's built-in opt-out list, so its .node addon is loaded via native require instead of being bundled — usually zero config needed; add serverExternalPackages: ['better-sqlite3'] explicitly if using a wrapper package. Known residual friction: pnpm workspaces where the native package is a transitive dependency (vercel/next.js #68805, #85449) — Next 16.1 resolved the transitive case for Turbopack. Never import the driver in edge-runtime or client components; keep it in Node-runtime route handlers/server components only.
- [verified] In Next.js dev, module re-evaluation on hot reload creates duplicate DB connections unless the instance is cached on globalThis
    Long-standing, well-documented behavior (vercel/next.js #45483, discussions #26427/#23867): Fast Refresh re-evaluates modules, so a module-scope `new Database(...)` or `new PrismaClient()` accumulates instances. Standard fix: create the db/ORM instance in one module and stash it on globalThis in non-production (`globalThis.__db ??= createDb()`). For better-sqlite3 the symptom is stale/leaked file handles rather than pool exhaustion, but the same singleton pattern applies. Also set `db.pragma('journal_mode = WAL')` and a busy_timeout once at creation.
- [likely] Migration workflows: drizzle-kit generate/migrate produces auditable plain SQL; Prisma 7 migrate is schema-driven but changed significantly in v7
    Drizzle: schema lives in TypeScript; `drizzle-kit generate` emits plain .sql migration files you can hand-edit (important for data backfills during statement-format changes), `drizzle-kit migrate` applies them, `drizzle-kit push` for prototype-speed schema sync (SQLite push support is mature). Prisma: schema.prisma DSL; `prisma migrate dev` generates SQL + tracks history in a _prisma_migrations table, but in v7 it no longer auto-generates the client or runs seeds, and CLI config moved to prisma.config.ts. Community consensus (2026 comparisons: Bytebase, Makerkit, dev.to) is that Drizzle's closer-to-SQL migrations are easier to audit/modify while Prisma's are faster when the happy path works.
- [uncertain] Runtime overhead: Drizzle+better-sqlite3 remains faster and lighter than Prisma 7 for SQLite, though Prisma 7 closed most of the historical gap
    Drizzle is a thin query builder over the driver (~57KB core, no codegen step at runtime); pre-v7 Prisma with the Rust engine was often 10-100x slower on local SQLite microbenchmarks. Prisma 7's TypeScript client claims up to 3x faster queries and ~90% smaller bundles vs Prisma 6, and 2026 comparisons say it closed ~70% of the gap — but Drizzle still wins cold start and per-query overhead on SQLite. All third-party benchmark numbers here should be treated as directional, and Drizzle's own benchmark page is vendor-published.
- [likely] Prisma has a history of rough SQLite lock/timeout ergonomics
    prisma/prisma #10403: SQLite 'database is locked' surfaced as an unclear mapped error (DatabaseBusy mapped to SocketTimeout in the old quaint layer); #2955: long-standing request for a configurable SQLite busy timeout; prisma-engines #4675 questioned Prisma's use of exclusive locking mode. Some of this is Rust-engine-era and the v7 better-sqlite3 adapter lets you pass driver options (including timeout) directly, which improves matters — but community reports on v7-era SQLite lock behavior are still thin. With Drizzle you configure busy_timeout/WAL directly on the better-sqlite3 handle, so behavior is explicit.
- [verified] Type safety: both are excellent; Drizzle infers types from TypeScript schema, Prisma generates a client from DSL
    Drizzle: schema declared in .ts, types inferred end-to-end with no generate step for the core API (select/insert types via $inferSelect/$inferInsert); raw-SQL escape hatch keeps types at the boundary. Prisma: types come from a codegen step (now `prisma generate` into a mandatory custom output path in v7); the generated client is very ergonomic for relations/nested writes. Practical difference: Drizzle types update instantly on schema edit; Prisma requires regeneration, and v7's ESM-only generated client constrains project config.

RECOMMENDATION: Use Drizzle ORM (pin stable 0.45.x now; move to 1.0 when it exits RC — rc.4 shipped Jun 27, 2026) with better-sqlite3 v12.x as the driver. Justification for this specific app: (1) statement import and reconciliation want atomic, synchronous batch transactions — Drizzle's better-sqlite3 driver is the only mainstream option where db.transaction((tx) => {...}) is truly synchronous (verified in source), eliminating async interleaving inside a batch and giving better-sqlite3's class-leading insert throughput (orders of magnitude faster than @libsql/client for local files); (2) drizzle-kit generate emits plain, hand-editable SQL migrations — auditable and safe for a finance schema that will evolve as new bank/brokerage formats are added; (3) zero runtime codegen and minimal overhead on a local single-user DB. Setup specifics: create the connection in one module with a globalThis-cached singleton to survive dev hot-reload; at creation run pragma journal_mode=WAL, busy_timeout (e.g. 5000ms), and foreign_keys=ON; rely on Next.js's default externalization of better-sqlite3 (add serverExternalPackages: ['better-sqlite3'] only if wrapping it), use Next >=16.1 if on pnpm workspaces, and keep all DB imports in Node-runtime server code. If native-module rebuilds ever become annoying, the escape hatch is Drizzle's node:sqlite driver (sync, zero native deps, stable in Node 26) — a config-level swap, not an ORM rewrite. Avoid Prisma 7 here not because it's bad (its Rust-free client + better-sqlite3 adapter are GA and solid) but because its async-only transactions, codegen step, ESM/config migration churn, and historically weaker SQLite lock ergonomics buy you nothing for a local single-user file DB; avoid @libsql/client because its local-file write performance and async API are strictly worse for this workload unless you someday want Turso sync.
